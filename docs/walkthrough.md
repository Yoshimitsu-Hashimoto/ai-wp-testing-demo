# 講座の流れと再現手順

講座「AIと作るWordPressサイト」で実演した流れを、自分の環境で再現するための手順です。各ステップで Claude Code に渡したプロンプトも載せています。

**仕様書 → 構築 → テスト計画 → テスト → バグ管理表 → GitHub Issue → 修正 → 再テスト**

## 0. 準備

1. このリポジトリを自分のGitHubアカウントにフォークし、cloneする（Issueを作るため）。
   - フォークは初期状態でIssueが無効になっている。フォークの Settings → General → Features で Issues を有効にする。
   - `gh issue create` が自分のフォークにIssueを作るよう、cloneしたフォルダで `gh repo set-default <自分のアカウント>/ai-wp-testing-demo` を実行する。
2. [README](../README.md) の「ローカル環境の起動」と「テスト（Playwright）」の手順で、環境とPlaywrightを用意する。
3. Claude Code をこのリポジトリのフォルダで起動し、Playwright MCP の利用を許可する。
4. GitHub CLI（`gh`）でログインしておく（`gh auth status` で確認）。

各ステップの前に `./scripts/seed.sh` を実行すると、テストデータと確認用メールボックスが初期状態に戻ります。

## 1. 仕様書を読む

[docs/spec.md](spec.md) と [docs/test-data.md](test-data.md) を読みます。曖昧な仕様との違いは [docs/spec-ambiguous-example.md](spec-ambiguous-example.md) にまとめています。

## 2. AIでWordPress化する（実績一覧の絞り込み）

`start` ブランチは、実績一覧の業種による絞り込みを実装する前の状態です。

```bash
git switch start
```

プロンプト：

```text
このリポジトリは講座用のWordPressサイトです。theme/hinata がテーマです。
制作実績一覧（/works/）に、業種による絞り込みを実装してください。

- 満たすべき仕様：docs/spec.md の「2. 制作実績一覧」（SPEC-02, 03, 07, 08, 09 と補足）
- デザイン：static-site/works.html の絞り込みボタンの見た目に合わせる（CSSは theme/hinata/assets/css/main.css の .filter-row にある）
- 絞り込みはURLの ?industry=<業種のスラッグ> で行う。業種はカスタムタクソノミー industry
- 実装したら、ブラウザで /works/ を開き、業種を選んで表示が変わることを確かめてください
```

講座では時間の都合で、この後は完成済みの状態から続けます。

## 3. AIでテスト計画を作る

ここからは、意図的なバグが入った `buggy` ブランチを使います。

```bash
git switch buggy
./scripts/seed.sh
```

プロンプト：

```text
あなたはこのWebサイトのテスト担当です。docs/spec.md（仕様書）と docs/test-data.md（テストデータ）をもとに、テスト計画を作って docs/test-plan.md に保存してください。

- 各テストケースに、テストID、仕様ID、前提条件、操作手順、期待結果を書く
- 正常系・異常系・境界条件（0件、未入力、形式の誤り、未公開のデータなど）を含める
- 期待結果は仕様書とテストデータから決める。仕様書に書かれていないことは合否を決めず「仕様の確認事項」として別に書く
- 合否の判断は仕様書とテストデータだけで行う。テーマのコード（theme/）、git の履歴や差分、他のブランチは見ない
```

AIが作った計画を人が確認します。たとえば次の観点が入っているかを見ます。

- 絞り込み結果が0件の場合（業種「医療」）
- 「すべて」に戻したときに件数と内容が元に戻るか
- 下書きの実績が一覧・トップ・詳細URLに出ないか
- 制作年が未入力の実績（さくら学習室）の詳細
- 必須項目の未入力を1つずつ確かめているか
- 同意チェックの確認を、他の項目を正しく入力した状態で行っているか
- 送信完了の表示だけでなく、メールの到着も確かめているか

## 4. AIでテストする

プロンプト（ブラウザでの確認）：

```text
docs/test-plan.md のテストケースを、Playwright MCP のブラウザで実際に操作して確かめてください。
サイトは http://localhost:8090/ 、確認用メールボックスは http://localhost:8091/ です。管理画面にはログインしないでください。
各テストケースの結果（合格／不合格）と、不合格の場合は実際の結果を記録してください。
この段階ではコードの修正はしないでください。合否は仕様書とテストデータだけで判断し、テーマのコード、git の履歴や差分、他のブランチは見ないでください。
```

プロンプト（自動テストとして保存）：

```text
docs/test-plan.md のテストケースを、Playwright Test のテストコードとして tests/e2e/ に書いてください。
- 設定は playwright.config.ts にある。確認用メールボックスは Mailpit の API（http://localhost:8091/api/v1/messages）で確かめる
- テスト名にテストIDと仕様IDを入れる
- 実行前に ./scripts/seed.sh を実行し、npm test で実行して結果を報告する。不合格のテストがあっても、期待結果やコードを変えない
- テストは仕様書とテストデータをもとに書く。テーマのコード（theme/）、git の履歴や差分、他のブランチは見ない
- 不合格のテストのスクリーンショット（test-results/ の中）は、実行のたびに上書きされるため docs/evidence/ にテストIDが分かる名前でコピーしておく
```

## 5. バグ管理表とGitHub Issue

Issueにするバグは、バグ管理表を見て人が1件選びます（講座では業種の絞り込みのバグを選びました）。

プロンプト：

```text
テストで不合格になった結果を、docs/bug-list.md のバグ管理表に記録してください。
- 同じ原因と考えられる不合格は1件にまとめる
- 期待結果は仕様書の記述に基づいて書く
- 証拠には、docs/evidence/ に保存したスクリーンショットのパスと、不合格になったテストIDを書く

記録したバグのうち BUG-<番号> を、GitHub Issue にしてください。
.github/ISSUE_TEMPLATE/bug_report.yml の項目（バグID、仕様ID、概要、再現手順、期待結果、実際の結果、重要度、証拠、修正後の確認条件）を本文に含め、ラベル bug を付けて gh issue create で作成してください。作成したらIssueのURLをバグ管理表に記入してください。
```

## 6. AIで修正して再テストする

プロンプト：

```text
GitHub Issue #<番号> を gh issue view で読み、修正してください。
- 新しいブランチ fix/issue-<番号> を作って作業する。コミットするのはテーマの修正だけにする
- 仕様書（docs/spec.md）に合うように実装を直す。テストの期待結果は変えない
- 修正後、Issueの「修正後の確認条件」にあるテストを実行して合格を確かめ、続けて npm test で全テストを実行する
- 結果をIssueにコメントし、バグ管理表の対応状況を更新する
```

Issueを作ったら、GitHubの画面でIssueを開き、`docs/evidence/` のスクリーンショットをドラッグ＆ドロップで添付します（`gh issue create` では画像を添付できません）。

修正したバグのテストが合格し、他のバグのテストは不合格のまま残ることを確かめます。

## 解答例

`reference` ブランチに、テスト計画・テストコード・実行記録・バグ管理表とIssueの記入例があります。講座のあとで、自分の結果と比べてください。

```bash
git switch reference
```
